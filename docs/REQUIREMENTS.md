# Соответствие ТЗ и границы готовности

Основа — документ «Техническое задание на разработку системы обратной связи и предложений сотрудников в рамках хакатона ГК “Модус Трейд”», проект для согласования, разделы 2–6. Статус «реализовано» относится к исходникам; «проверено» — к указанному способу проверки; внешняя приёмка оценивается отдельно.

| Требование | Реализация / материалы | Проверка | Внешняя граница |
|---|---|---|---|
| 2.2 Сотрудник, руководитель, администратор | Роли, участники, правила доступа | Локальные тесты прав, selfcheck | Реальный штат компании ещё не принят |
| 2.3 Создание и регистрация | Форма, диалог, подтверждение карточки | Ядро; selfcheck создания | ИИ-диалог требует отдельного подключения |
| 2.3 Передача ответственному | Категории, основной/резервный, назначение руководителем | Тесты маршрутизации и недоступности | Регламент компании требуется согласовать |
| 2.4 Статусы и сроки | Работа, уточнение, проверка, возврат, принятие | Полный цикл ядра и selfcheck | Рабочие SLA пока учебные |
| 2.4 Комментарии и материалы | Общая комната, PNG/PDF/TXT/DOCX, редакции, решения по файлам | 20 комнат, 60 HTTP-скачиваний и SHA-256 | Доставка бинарных файлов провайдерами не принята |
| 2.4 Уведомления | Внутренние уведомления и реестры внешней доставки | Локальные тесты, синтетические транспорты | Реальный WhatsApp-вход/квитанции остаются незакрытым пунктом |
| 2.4 Поиск и история | Фильтры, карточка, журнал действий, экспорт | Тесты ядра; UI исходного выпуска | Промышленная нагрузка не проверена |
| 2.4 Повторяющиеся проблемы | Сходные случаи и аналитика доступного контекста | Тесты разграничения и метрик | Бизнес-полезность требует пилота |
| 2.5 Результат и обратная связь | Исполнитель предъявляет, автор принимает/возвращает | Самопроверка с возвратом и повторным результатом | Реальные решения компании не имитируются |
| 2.6 Конфиденциальность | Серверные проверки ролей и вложений | HTTP 401/404, изоляция чужих дел | SSO, HTTPS и политика данных перед внедрением |
| 3.1 Продуктовая проработка | PRODUCT.md, PILOT_PLAN.md | Документированная концепция | Численные KPI согласуются с заказчиком |
| 3.2 Интерфейс и сценарии | Кабинет, карточки, общая комната, аналитика | Локально работающий UI; runbook | Физический телефон отдельно от узкого viewport |
| 3.3 Архитектура и технологии | ARCHITECTURE.md, исходники компонентов | Проверяемый состав и хеши | Не заменяет нагрузочное/эксплуатационное обследование |
| 3.4 Корпоративные интеграции | Описаны назначение, данные, направления | Контракты/фикстуры коннекторов | Bitrix/1С не обязательны ТЗ и не заявлены как принятые |
| 3.5 Данные и безопасность | Синтетические случаи, исключённые секреты | Состав пакета, хеши, права | Разрешения на данные реальной компании отдельно |
| 3.6 Развитие | Ограниченный пилот → каналы → инфраструктура → расширения | PILOT_PLAN.md | Будущие этапы не выдаются за функции MVP |
| 4.1 Концепция, прототип, архитектура, развитие, показ | README + docs + рабочий интерфейс | Локальный исходный пакет | Видеопоказ/веб-тур обозначаются отдельно |
| 4.2 Исходный код и репозиторий | source/ + provenance + частный GitHub | Сверка 184 файлов, чистый запуск | Доступ организатора проверяется отдельной квитанцией |
| 4.2 Runbook, данные и ограничения | DEMO_RUNBOOK.md, TEST_DATA.md, LIMITATIONS.md | Повторяемые команды и selfcheck | Нет внешнего ИИ/мессенджера без настройки |

Исходный b8 имеет отдельную более широкую историю проверок Windows-комплекта: 297 тестов, 294 пройдены, 3 opt-in bridge-теста пропущены. Эта цифра не присваивается заново лёгкому пакету: его фактические результаты приведены в `evidence/VALIDATION.md`. Тестирование mock-провайдера не доказывает входящее сообщение с физического телефона или фактическую доставку.
